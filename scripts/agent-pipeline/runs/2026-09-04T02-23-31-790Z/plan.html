Plan reviewer-approved

Artist page tabs are currently client-only state (activeTab) instead of URL-addressable routes, making individual views non-shareable and requiring inefficient data management. Navigation between tabs causes unnecessary refetches due to the monolithic load design.

Requirements

  • Create nested route structure: migrate from /artist/[slug]/ to /artist/[slug]/[view]/ where [view] is one of: feed, music, posts, photos, videos, shop
  • Split per-view data loading: refactor +page.server.ts to lazy-load only the data needed for each view, triggered on first navigation to that view
  • Implement client-side view caching: cache loaded view data in a Svelte store so navigating away and back to an already-loaded view does NOT refetch or invalidate
  • Implement URL-driven navigation: update +page.svelte to navigate via goto(url) on tab clicks instead of mutating activeTab state, and derive activeTab from URL params
  • Prevent page reload on navigation: use SvelteKit's client-side goto() instead of full-page navigations or invalidateAll()
  • Handle missing/invalid view param: default to 'feed' view if [view] param is missing or invalid; preserve existing 404 behavior for invalid artist slug
  • Support direct URL access: users can navigate directly to /artist/[slug]/music or /artist/[slug]/posts and see the correct view with its data loaded

Out of scope

  • Refactoring the Tabs component to handle generic URL routing (keep it view-agnostic)
  • Changing artist profile data or subscription logic (only reorganize data flow, not business logic)
  • Implementing Shop view functionality (already stubbed as 'coming soon', no data loading needed yet)
  • Adding new views or tabs beyond the current six
  • SEO optimizations like canonical URLs or structured markup per view

Subsequent tab clicks within that session are genuinely free of refetch via the cache — this only affects the very first view per full page load, not tab switching, so it doesn't undermine the no-refetch requirement.

Review journey

Round 1needs-revision
  • Rubric 5 (internal consistency): the decision to move data loading into [view]/+page.ts (universal load) and return an un-awaited event.fetch(...) promise claims this 'preserves the existing {#await content} streaming/skeleton contract.' It doesn't. SvelteKit's promise-streaming (the chunked text/sveltekit-data flush) is implemented only for **server** load nodes — confirmed in node_modules/@sveltejs/kit/src/runtime/server/data/index.js, where only load_server_data output goes through server_data_serializer_json/chunks. A universal load's promise gets no such treatment: during SSR, Svelte's {#await} simply renders the pending branch synchronously, and the universal load then re-runs a second time in the browser after hydration (this is normal SvelteKit behavior for +page.js), firing a second event.fetch. So for requirement 7 (direct URL access), the SSR response will always render only the skeleton — real content shows up only after a second client-side round trip — a genuine regression from today's true SSR-streamed content that the plan neither flags as a tradeoff nor accounts for elsewhere.
  • Rubric 4 (verifyCommands gap): the plan justifies skipping automated coverage of the goto-on-click / URL-derived-activeTab wiring (spec requirements 4 and 5, arguably the riskiest new logic) by asserting 'no unit-test infrastructure in this repo currently mounts a +page.svelte... confirmed: no +page.svelte.spec.ts exists anywhere in src/routes.' That's factually wrong — src/routes/page.svelte.spec.ts already does exactly this, rendering ./(app)/+page.svelte via vitest-browser-svelte's render(). Combined with the vi.mock('$app/navigation', ...) technique the plan itself references for the cache-store test, a real automated test asserting goto (not invalidateAll) fires with the correct URL on tab click is achievable and should be added to verifyCommands instead of relying solely on manual click-through.
Round 2needs-revision
  • Requirement 'Split per-view data loading: refactor +page.server.ts' has no decision handling the existing votePoll action (src/routes/(app)/artist/[slug]/+page.server.ts:74-100). Decision #3 reduces this file to a one-line redirect load, and no other decision creates actions on the new [view]/+page.server.ts — the fileMap entry for line 74 flags that votePoll 'must move' there, but no decision item actually performs that move, and no spec/verifyCommand covers it. As written, poll voting on the artist page silently breaks after the migration (the form action posts to the [view] route, which would have no matching action).
  • Decision #3's redirect snippet is broken: redirect(307, \/artist/${params.slug}/feed}\) has a stray closing brace before the closing backtick, producing a literal .../feed} URL. This is the entry point for every existing /artist/[slug] link and for requirement 6 (default to 'feed' when view is missing) — as written it doesn't satisfy that requirement, it redirects to a broken URL.
  • No verifyCommand exercises the root +page.server.ts redirect at all — it's deferred to a manual yarn dev click-through (decision #3 and the final manual-verification step). Given that reliance on manual-only checking, the typo above would not be caught by any of the listed verifyCommands; a one-line automated spec (or including it in an existing spec) is needed for this load-bearing entry-point behavior.
